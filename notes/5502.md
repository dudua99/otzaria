# Issue #5502 — feature notes (verify everything)
Type: search behaviour / FEATURE (milestone 0.9.99; labelled bug). Assignee: none. Maintainer stance: none. NEEDS_DECISION.

## Requested behavior
Report: "searching 'רבינו בחיי' in the search window does not bring up the book 'רבינו בחיי על התורה'; but writing '@רבינו בחיי' finds only 'על התורה' and not 'רבינו בחיי אבן פקודה' (חובות הלבבות)". Reporter has the plugin `com.local.author-search` ("חיפוש לפי מחבר") installed (r5502).
Findings:
- `@name` is a TITLE/CATEGORY scope, not an author filter: lib/search/utils/category_query_parser.dart L10-16, L52-62; resolver layers ~L138-139 = exact title, whole words, partial containment, typos — no author layer. So "@רבינו בחיי" → the book/category titled "רבינו בחיי", by design. חובות הלבבות's title doesn't contain the name.
- Part 1 ("search window doesn't bring the book") is ambiguous: full-text search returns text hits, not books; the library/book-title search is a different field. Needs the reporter's exact screen.
Question: should `@name` also scope to books whose AUTHOR matches name?
DEFAULT (if owner says proceed): add an additive author layer to `@` resolution — books whose normalized author equals the name (or the name equals a known author alias) are added to the facets, after the title layers; no fuzzy author matching (precision). Reply to the reporter about part 1 asking for the exact window.
Acceptance (default):
- "שלום@רבינו בחיי" scopes to "רבינו בחיי על התורה" AND all books whose author normalizes to "רבינו בחיי ..."? → NO: exact normalized author equality only; "רבינו בחיי אבן פקודה" ≠ "רבינו בחיי". So the reporter's example would still not match unless an alias table maps both — state this in the PR. If the owner wants prefix author matching ("author starts with name"), that is a second decision.
- Existing title/category results unchanged; `notFoundNames` unaffected when an author match exists.
