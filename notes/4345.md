# Issue #4345 — feature notes (verify everything)
Type: FEATURE (milestone 0.9.99). Assignee: none. Maintainer stance: none. NEEDS_DECISION (data-model extension).

## Requested behavior
Allow adding HebrewBooks PDF add-ins (and generally PDF/external books) to שמור וזכור (learning tracker).
Current design (blocker): add_books_to_tracking_dialog.dart ~L87-94: "שמור וזכור נשען על מזהי seforim.db בלבד; ספר אישי/חיצוני מחזיק מזהה ממרחב אחר שעלול להתנגש עם ספר רשמי אקראי, ולכן אינו נתמך" — progress is keyed by official seforim.db book id, and units come from the DB TOC.
Question: extend tracking to non-official books (PDF/HebrewBooks/personal)? If yes, with which units — PDF pages, or the PDF outline (bookmarks) when present?
DEFAULT: support PDF books keyed by a stable string identity (`BookIdentity.indexedFilePath` / external id, namespaced e.g. `pdf:<id>`) in a separate key space (no collision with numeric ids); units = PDF outline leaves when the PDF has an outline, else pages ("עמוד 1..N"); opening an item opens the PDF at that page.
Acceptance (default):
- "Add books" dialog lists PDF/HebrewBooks books (marked with their source icon) and allows tracking them.
- Progress for these books persists separately, never colliding with official ids; existing data untouched (no migration of old keys).
- Book detail screen works with page/outline units; mark range works.

Owner decision (23.11): try again WITH an explicit design for identifying a personal PDF across devices.
Required:
- Design first (write it in the PR body): a stable cross-device identity for a tracked PDF that does not depend on per-device negative numeric keys — e.g. a content fingerprint (hash of file size + first/last N bytes, or full SHA-256 computed once in the background) plus the original file name as a fallback hint; HebrewBooks PDFs by their HebrewBooks id. Progress and every linked record are keyed by that identity, never by a per-device number.
- Backup/restore and BOTH merge paths (`BackupImportMerge.mergeShamorZachor` and the rolling-archive `BackupMerge`) must carry identity + progress together; a backup from device A merged into device B must land on the same PDF or stay unattached (never on a different local PDF). Reproduce the maintainer scenario (two devices both assign key -1 to different PDFs) as tests for both merge paths FIRST (must fail on the old head).
- Migration of existing tracked entries (negative keys) to the new identity, idempotent, off the startup path.
- If the design needs a maintainer decision you cannot make (e.g. hashing cost), state it as an explicit open decision with the measured cost.
