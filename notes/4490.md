## Requested behavior
Add tests (and only targeted fixes if a test exposes a real failure) for DB read-worker lifecycle recovery after #4423.
1. Extra commands after recovery was SENT: hold the reply to `lifecycleState` after it is sent, send another lifecycle change + a read, then release both recoveries separately. Assert: a sync signal proves the first command was sent before the extra change was queued; completing the first recovery doesn't let the read bypass the new state; latest state and `mustClose` are kept; command quota not exceeded; the read completes per the final state with no dangling wait.
2. Worker teardown while the recovery command awaits its reply (after `lifecycleState` was sent), including when a further change is already accumulated in the deferred record: all read/resume waiters finish within an explicit timeout with the expected result/error; no unhandled error, dangling Future or double Completer completion; a new worker can open and read afterwards.
3. Integration under load: fill the control queue through a REAL worker and call `SqliteDataProvider.closeForExternalWrite()`: the write body never starts without a release ack; gate and hold return to normal after the failure. `DbReadWorkerBusy` rejection on refresh/reset paths gives the user a clear failure and retry works after recovery. Measure latency until a long read is cancelled when the 4 slots are busy in open/resume and an extra close/suspend is deferred; document the result and the decision.
