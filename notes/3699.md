Maintainer stance: Y-PLONI 03.11: matches implementation; "להוסיף לכל אירוע שנתי־עברי רלוונטי בחירה בין אדר א׳ לאדר ב׳ בשנה מעוברת, ולשמור אותה ב־JSON ובעריכה. לשמר ברירת מחדל תואמת לאירועים קיימים ולהחיל אותו מיפוי בתצוגה ובמתכנן ההתראות".

## Requested behavior
Annual Hebrew events created in Adar of a common year always land in Adar I in leap years. Users need to choose (yahrzeit customs vs. bar-mitzvah in Adar II).
Acceptance:
- Event dialog: when recurrence is annualHebrew (and monthlyHebrew is unaffected) and the base date is in Adar (common year, month 12) or Adar I/II (leap year, 12/13), show a choice "בשנה מעוברת: אדר א׳ / אדר ב׳".
- Default for existing events = current behaviour (month 12 → Adar I; month 13 → Adar II). No migration needed: missing JSON field = legacy default.
- Event with base month 13 (Adar II) in a COMMON year must fall on Adar (month 12) — today `occurrenceCandidate` returns null and `_isOccurrenceStart` never matches, so such events vanish in common years (verify; fix together, it is the same mapping).
- Same mapping used in day cells, `occursOn`, `nextOccurrenceFrom`, alert planner, print, ICS/Google export where annualHebrew is converted (check google_calendar_service / ics export for RRULE generation of Hebrew dates — likely expanded instances; keep parity).

## Implementation sketch
- Add `final int? leapAdarMonth;` (12 or 13; null = legacy) or enum `AdarLeapRule { adarI, adarII }`, JSON key `leapAdar`.
- Single helper `int effectiveJewishMonth(int year)`: if base month ∈ {12,13} and rule set → leap ? (rule==adarII ? 13 : 12) : 12; legacy null → leap ? base : 12. Use in occurrenceCandidate and _isOccurrenceStart.
- Dialog control: AppSegmentedControl with two options, shown only when relevant. Plain Hebrew strings like the rest of the dialog (check convention).
