# Issue #4466 — feature notes (verify everything)
Type: FEATURE — Plugin SDK (milestone 0.9.99). Assignee: none. Author: Nathaniel-260 (maintainer) listed 6 team decisions before implementing; dudua99 18.11 verified the gap and suggested a direction. NEEDS_DECISION (Nathaniel's questions unanswered); defaults below.

## Requested behavior
New context-menu context `library-book`: plugin items appear when right-clicking a book in the library tree (and/or its ⋮ menu); the event carries book identity (`id`, `bookId`, `bookUid`, `type`, `source`) + `categoryPath`, no selection/position.
Decisions (Nathaniel's list) with DEFAULTS:
1. Where: both right-click and ⋮; plugin items are appended as a separate section below built-in items (Talmud format menu stays).
2. Which items: books only (categories = separate future context).
3. Permission: existing `reader.context_menu` (no new permission).
4. External-provider books: excluded in v1.
5. Load: max 2 items per plugin in this menu; if >1 plugin contributes, group under a "תוספים" submenu (cf. #3160).
6. Per-book filters: apply the same `bookTypes`/`bookSources` filters if they exist in the manifest schema; if not yet implemented, ship without and document.
Acceptance:
- Manifest with `"contexts": ["library-book"]` validates; item shows on right-click and ⋮ for matching books; click dispatches to the plugin with the identity payload (and `openPlugin` behaviour honoured).
- Disabled plugin / no items → menus unchanged.
- SDK docs (docs/plugin-sdk/API_REFERENCE.md + manifest reference) document the context and payload.

## Implementation sketch
- Registry + validation; `buildPluginContextMenuSection(context: 'library-book', payload: {...identity, categoryPath})` injected into both menus via one helper.
- Dispatch through `dispatchLibraryBookAction` so the plugin engine isn't woken unless `openPlugin`.
