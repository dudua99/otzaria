# Issue #4135 — in-book search: the book highlights the hits but the results list stays empty (sweep 26.11 part 3)
Type: bug. Checked on dev 4fe1973a4.

## Reporter (answered the bot)
- Example: "דרק ביאה" (probably "דרך ביאה") in "קובץ שיטות קמאי בכורות".
- Changing the search options (advanced mode / distance) as the bot asked did not help.
- Happens in some searches and not in others.
- palmoni5 (dev@4855ef9): #4145 fixed one possible scenario (a saved advanced mode with a single word); not proven to cover this report.

## Evidence (file:line on dev)
- lib/text_book/view/text_book_search_screen.dart:479 — only `_isSimpleSearch` (or a user regex) runs the local scan over the loaded content. Every other configuration goes to the engine (L561 `searchBookWithEngine`).
- L572-580 — engine results are post-filtered by exact `r.title.trim() == expectedTitle` and by section. If the index has no or stale entries for this book (book not indexed yet, a partial index, a title that changed in a library update), the list is empty.
- The highlights in the book do NOT come from the engine: `UpdateSearchText` (L242/L1215) makes the reader bloc highlight with its own pattern over the loaded text. So the two views can disagree: highlights shown, empty list. That is exactly the screenshot.
- Root of the engine route with the title post-filter: 70f95f154 (2026-01-08 "תיקון חיפוש בתוך הספר"); #4145 (694fa33ac) narrowed it only for a single word without options.

## Fix idea
When the engine route returns 0 results after the post-filter, while the book content is loaded (or can be loaded), run the local scan with the same words (`searchInContent`, wholeWord=true, same section range). If it finds hits, show them (the engine index is evidently stale for this book). A literal word sequence is narrower than any engine distance/advanced query, so every local hit is a legitimate hit of the engine query. No behavior change when the engine finds results.
Optionally log once (debugPrint / dev diagnostics) "engine returned 0, local scan found N" so stale indexes are visible.

Add: advanced settings (forces the engine route), a fake engine that returns [] for the book, content containing "דרך ביאה" twice → expect 2 results in the list. A second test: the engine returns results → no local scan is called (keep the engine semantics).

## Pitfalls
- Do not run the fallback for regex/user-regex or for queries with alternative words / spacing values that a local literal scan cannot express; then keep "no results".
- Keep request-id / mounted guards (`requestId != _activeSearchRequestId`).
- Section-limited search: pass the same range.
