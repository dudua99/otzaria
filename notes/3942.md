סוגר בעקבות רגרסיה בקדימות של קיצורי תוספים. בדקנו את סקריפט הייצור ב־Chrome עם `input`, `textarea` ו־`contenteditable`, ב־Ctrl וב־Cmd. במקרים הרגילים התיקון מעביר קיצור שלא טופל למארח ומכבד קיצור שהתוסף טיפל בו. בשני רצפי DOM תקינים הוא מקדים את מאזין התוסף וסוגר את הכרטיסייה במקום להעביר לו את ההקשה:

- מאזין בשדה מוסיף מאזין ל־`document`, וזה מוסיף מאזין ל־`window` במהלך אותה הקשה, אחרי שהמארח כבר סידר את המאזין שלו.
- מאזין בשדה משגר `keydown` נוסף באופן סינכרוני, ואז רושם מאזין ל־`window` עבור האירוע החיצוני. האירוע הפנימי מסיר את `_forwardLast` של החיצוני.

שני הרצפים עבדו ב־`dev` ונכשלו בגרסת ה־PR בכל שש הצירופים שנבדקו. בדפדפן לא נמצא פתרון ממוקד שגם נותן קדימות למאזיני התוסף וגם מבטל את פעולת ברירת המחדל באופן סינכרוני. #3942 נשאר פתוח.

Goal of the rework: Ctrl/Cmd+W (and the other host tab shortcuts the PR covered) must close the plugin tab also when focus is inside an input/textarea/contenteditable in the plugin, BUT plugin listeners keep priority: if any plugin listener handles the key (preventDefault/stopPropagation), the host must not act. Both DOM sequences the maintainer described must keep working exactly like dev: (1) a field listener adds a document listener which adds a window listener during the same keydown, after the host already arranged its own; (2) a field listener synchronously dispatches a nested keydown and registers a window listener for the outer event (the inner event must not clobber the outer one's state, e.g. no single shared _forwardLast). Write tests reproducing BOTH maintainer sequences in all 6 combinations (input/textarea/contenteditable x Ctrl/Cmd) plus the normal cases.
