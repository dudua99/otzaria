# Issue #5127 — feature notes (verify everything)
Type: FEATURE/UX (milestone 0.9.99; labelled bug). Assignee: none. Maintainer stance: none.

## Requested behavior
1. When the caret is in a text field and Otzaria loses OS focus (Alt+Tab away and back), the caret leaves the field; the user must click it again.
2. While typing in a book's in-book search field, switching to another tab and back puts focus on the reading area, not back in the search field.
Acceptance:
- (2) Per tab (pane): if the focused node when leaving the tab was a text input belonging to that tab (in-book search field, commentary search field), returning to the tab focuses that same field with caret at the end of its text (no select-all). Otherwise behaviour unchanged (reading area focused so arrows scroll — reading_screen.dart comment L297-303).
- (1) After window deactivate→activate, the previously focused text field regains focus. Reproduce first on Windows: Flutter normally restores primaryFocus on view refocus; if it does, find what steals it (candidates: `onWindowFocus` in core/window_listener.dart L698-720 synthesising key-ups / `WindowTabsSession.resume`, or a listener that calls `requestTabContentFocus` on activation). Fix the stealer rather than adding a second restore.
- A modal/dialog open at switch time is unaffected (existing `_paneBeforeModal` logic).

## Where in the code
- lib/tabs/reading_screen.dart: tab-switch listener (~L288-304) calls `_requestTabContentFocus(focusTarget)` → lib/core/focus_repository.dart `requestTabContentFocus(tabKey)` (L241) using per-tab requesters (L207-235). Modal return path L109-121.
- In-book search field focus nodes: text_book_screen.dart / book_common in-book search pane (find the FocusNode of the search field; FocusRepository already has restore helpers for find-ref — see ~L190-201 `restore`/`canRestore` pattern).
- Window activation: lib/core/window_listener.dart `onWindowFocus` L698; multiview focus: lib/core/windowing/multiview/view_focus_sync.dart (Linux only).

## Implementation sketch
- FocusRepository: `rememberTabFocus(tabKey, FocusNode)` updated on tab deactivation (TabsBloc listener: before switching, if `FocusManager.instance.primaryFocus` is an EditableText descendant inside the old pane, store its node); `requestTabContentFocus` first tries the remembered node if `canRequestFocus` and still attached, then falls back to the content requester.
- Clear the memory when the field is unfocused by the user (Esc / click in text) so we don't resurrect stale intent.

## Tests
