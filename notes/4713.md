# Issue #4713 — feature notes (verify everything)
Type: FEATURE (milestone 0.9.99; labelled bug). Assignee: none. Maintainer stance: Y-PLONI 19.11 "חושב יותר על הפרדה בין הצג הכל לאירועים קרובים" (prefers separating "show all" from "upcoming"); dudua99 18.11 diagnosis.

## Requested behavior
In the calendar events panel, "הצג הכל" lists every event since forever, including long-past ones. Add a separate "upcoming" view.
Acceptance:
- Three views: current day (default, unchanged), "אירועים קרובים" (new), "הצג הכל" (unchanged: everything, chronological).
- Upcoming = events whose next occurrence is today or later; a recurring event is listed once, at `nextOccurrenceFrom(today)`, and sorted by that date (then time/title via compareCalendarEventsByTime); recurring events whose recurrence ended (recurrenceEndDate / recurringYears) are excluded; multi-day events in progress today are included.
- Each row in upcoming shows the occurrence date (not the base date) — verify what the row renders today.
- Search query still overrides all views (existing behaviour).
- Empty message for upcoming: "אין אירועים קרובים".

## Implementation sketch
- Replace bool `showAllEvents` with enum `CalendarEventsView { day, upcoming, all }` (or add a second bool — enum preferred, single source). Keep it non-persisted like today (verify).
- Switch the button to `AppSegmentedControl<CalendarEventsView>` (DD-31a precedent: week/month selector uses AppSegmentedControl) with labels "יום" / "קרובים" / "הכל"; or keep one ActionButton cycling — prefer segmented (clearer).
- Upcoming list: `events.where(e => !e.nextOccurrenceFrom(today).isBefore(today) && (e.occursOn(next)))` → map to (event, next) → sort. Cap scanning cost: nextOccurrenceFrom loops ≤120 candidates per event; fine for hundreds of events, but compute in the cubit once per state change, not in build.
- Calendar strings here are plain Hebrew literals (not settingsText) — follow the file's existing convention; check if calendar has an arb catalog.
