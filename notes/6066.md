# Issue #6066 — offline mode: a plugin still checks the network and shows "updates available" (verify everything)
Type: BUG (no labels; milestone 0.9.99). Assignee: palmoni5. Maintainer stance: none. Reporter guessed "probably the plugin store, not the app" — but the app is what promises that offline mode ("מצב מנותק") stops network access, and the gate that should enforce it does not look at offline mode at all.

## Report
Offline mode on → a bar "יש עדכונים לתוספים" still appears (622x73 screenshot). Clicking it opens the store tab, which the app correctly blocks: "התוסף ... דורש חיבור אינטרנט / התוסף חסום כל עוד אוצריא במצב מנותק" (lib/tools/view/tool_tab_screen.dart:294-297, ToolUnavailableReason.pluginRequiresInternet).

## Evidence on dev 4fe1973a4
- The app's OWN plugin-update check is gated: PluginUpdateCheckService.updatesAllowed() returns false in offline mode (lib/plugins/services/plugin_update_check_service.dart:49-63). So the banner does not come from PluginUpdatesCubit/plugin_update_chip — it comes from the store PLUGIN (its background/startup runtime, which calls network.* / fetch itself and then shows its own notification via the `notifications` bridge domain, plugin_bridge_adapter.dart:1343).
- Offline mode only HIDES/BLOCKS plugin UI: `blockedInOfflineMode` (installed_plugin.dart:77) is used by tool_catalog_entry.dart:167/212, tools_launcher_panel.dart:993 and main_window_screen.dart:577 (`filterForOfflineMode`). It is NOT used by:
  - the network gate `evaluatePluginNetworkAccess` (lib/plugins/services/plugin_network_gate.dart:23-47) — no offline check; used by bridge network.* (plugin_bridge_adapter.dart:8835, :1464, :9070), WebView request gate (plugin_webview_host.dart:669) and declarative actions (declarative_host_action_executor.dart:230);
  - `resolvePluginNetworkPolicy` (plugin_network_policy.dart:41ff, CSP/WebKit rules) — no offline check;
  - background runtime: PluginBackgroundHost (_syncBackgroundPlugins L160-182 keeps every `enabled` plugin; _activateOnDemand L200ff) and PluginLazyActivationService — no offline check (`git grep -n "blockedInOfflineMode\|isOfflineMode" lib/plugins/services/plugin_lazy_activation_service.dart lib/plugins/view/plugin_background_host.dart` is empty).
- Root cause history: offline gating for plugins was done at the UI entry points only (3b20a2b68 "הקשחת מערכת התוספים", ee2228ccb palmoni5 15.7 "שערי הפתיחה ורענון ה-transient יושרו לתנאי הסינון (blockedInOfflineMode)" — tools_screen only). The network gate (3b20a2b68) never got the offline condition, so a background runtime of a network plugin keeps network access in offline mode.

## Fix direction (minimal, one root)
Make the single network decision offline-aware: in `evaluatePluginNetworkAccess` return a new `PluginNetworkDecision.offlineMode` (or reuse a blocked value) when `Settings keyOfflineMode == true`, BEFORE the permission lookup; mirror it in `resolvePluginNetworkPolicy` (return `PluginNetworkPolicy.none` in offline mode) and fire `PluginNetworkPolicy.notifyChanged()` when the offline setting toggles (find the settings write for keyOfflineMode; connectivity_status_service.dart:60 reads it). Map the new decision in plugin_bridge_adapter.dart:8842-8870 to a clear error (e.g. 'error.offline_mode') so plugins can stay quiet.
Optional, only if tiny: do not activate background runtimes of `blockedInOfflineMode` plugins in offline mode (plugin_background_host _activateOnDemand). Prefer the gate fix alone if it already blocks the banner path (the plugin's check fails → no banner).
Do NOT touch PluginUpdateCheckService (already correct) and do NOT change plugin store code (separate repo).

## Tests (must fail on dev)
- test/plugins/services/plugin_network_gate_test.dart: plugin with networkEnabled + granted permission + allowlisted URI → `allowed` online; with Settings keyOfflineMode=true → not allowed (new decision). Fails on dev (returns allowed).
- Same for resolvePluginNetworkPolicy → `none` in offline mode.
- Bridge: network.fetch from a granted plugin in offline mode throws the offline error (existing bridge network tests as harness).
- Keep green: plugin_network_gate_test, plugin_background_host_test, tools_screen_transient_resolution_test, plugin_side_panel_test, plugin_update_check_service tests, `flutter analyze`.

## Pitfalls
- Plugins whose network permission the user turned off are NOT blocked in offline mode by design (ee2228ccb) — the gate already denies them via permissionMissing; keep that.
- Loopback/local plugin servers (loopbackHosts in PluginNetworkPolicy): decide whether offline mode should block localhost — keep loopback allowed (it is not internet); say so in BODY.
- Settings may be uninitialised in tests: treat read failure as "not offline" in the gate? No — follow updatesAllowed() style but fail OPEN only for the offline flag read (otherwise every gate test breaks); explain in BODY.
- Refs #6066 (reporter suspects the store plugin too; the store may also want its own offline check — mention for the store repo, don't change it).
