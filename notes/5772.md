# Issue #5772 — bug notes (verify everything)
Type: BUG (milestone 0.9.99, from-app, Windows 11, 0.9.98+99803). Assignee: none. Maintainer stance: none. No open PR on this. Reporter: with many tabs in the vertical tab column (side), on startup the column is scrolled to the top although the active book is further down, so closing it needs scrolling; a book opened from the library is added at the end of the column and is also out of view. Expected: the column keeps the active tab visible automatically (unless the user scrolled it).
Screenshot exists — do not open.

## Root
Missing behavior since the vertical strip was added: ae73306ba (palmoni5, 17.08 "כרטיסיות אנכיות בצד") — no code ever scrolls the strip to the current tab (`git log -G"ensureVisible|animateTo\(|jumpTo\("` on the strip files finds only the drag edge-scroll). Not a regression; still a bug (labelled, expected behavior).

## Requested behavior
When the column is scrollable (`scrollable: true`, vertical): on first layout and whenever `currentTabIndex` changes (startup restore, SetCurrentTab, AddTab, Ctrl+Tab, Ctrl+1..9, closing a tab), scroll the minimum amount so the active tab is fully visible (no scroll if already visible). Jump on first layout, short animation afterwards. Never during a drag (edge auto-scroll owns the position then). Manual scrolling by the user is not fought: only an index change triggers it.
Acceptance:
- Widget test: 40 tabs, column height for ~10, `currentTabIndex = 35` at first pump → tab 35 is within the viewport (fails on dev: offset 0).
- AddTab at the end → the new tab is visible after settle (fails on dev).
- Active tab already visible → offset unchanged; during a drag reorder no jump.

## Implementation sketch
- In `ReadingTabStrip`: when `widget.scrollable && selectedIndex != null` and it changed (or first frame), post-frame compute `[start, end]` of that tab from `_geometry` and call `jumpTo`/`animateTo` clamped to the viewport; skip while a drag session/auto-scroll is active.
